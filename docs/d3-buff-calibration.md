## 方法

探针 `cmd/screenprobe` 一条命令完成：临时接管焦点 → 按 `1,2,3,4` → 立刻还原焦点 → 连拍并逐张报告采样点。

```
go run ./cmd/screenprobe -process "Diablo III64.exe" -activate \
  -press "1,2,3,4" -settle 600 -burst 8 -interval 500 \
  -px "603,945;667,945;729,945;793,945;859,945;921,945" \
  -out dist/d3-buff.png
```

## 槽位 2~6 的交叉验证

槽位 2~6 当前不是 Buff 技能（按下无变化），无法用「按键看变化」逐个验证，因此改用几何交叉验证：

| 项 | 数值 |
| --- | --- |
| 实机扫描的 6 个图标中心间距 | **恒为 63px** |
| D3keyHelper 基准横坐标的间距 | 89 / 88 / 89 / 93 / 87 |
| 按 `scale = 1025/1440` 换算后 | 63.4 / 62.6 / 63.4 / **66.2** / 61.9 |

两者最大偏差 3.2px（第 4 个间距）—— 源于基准数据是**手工测量**的，本身并不严格等距。
采样点落在图标边缘的 Buff 指示区内（槽位 1 实测：指示区覆盖图标左边缘一带），3px 偏差不会让它滑出。

结论已固化为单元测试：

- `TestD3BuffSampleSpacingMatchesGameLayout` —— 用实机间距 63px 校验换算后的 6 个采样点间距（容差 5px）
- `TestD3BuffSamplePointMatchesMeasuredBaseline` —— 槽位 1 的实测值 `(603,945)` 作为回归基线

**因此槽位 2~6 直接采用 D3keyHelper 的基准数据，不再单独标定。**

## 保持 Buff 的实现依据

D3keyHelper 的保持逻辑（`d3keyhelper.ahk:806` 起，`case 4:` 分支）：

```ahk
case 4:                        ; 策略 = 保持buff
    magicXY := getSkillButtonBuffPos(D3W, D3H, nskill, buffpercent)
    crgb := getPixelRGB(magicXY)
    if (crgb[2] < 95)          ; 绿通道低于 95 → Buff 断了
        ...补一次按键
```

本项目 `internal/engine` 的实现与之等价（取反表达）：注入的守卫返回「Buff 是否仍生效」，
生效则**跳过本次点按**并 150ms 后重采样，断开才补。同时复刻了它的优先级仲裁
（`d3keyhelper.ahk:744`）：高优先级 Buff 生效期间，低优先级技能让路。

D3keyHelper 虽多年未更新，但该逻辑在暗黑3 中至今可用（玩家实测），
因此这里**直接采用其结论**，不再自行推导替代算法。

## 其它宽高比

D3keyHelper 的公式以**窗口客户区水平中线**为锚点：

```
x = Round(D3W/2 - (3440/2 - 基准X - percent*按钮宽) * D3H/1440)
```

即「从屏幕中线出发、按高度比例偏移」，因此**不假设 16:9**：换任何宽高比，只要暗黑3 的技能栏
相对中线居中（游戏自身行为），公式就自适应。本项目 `d3BuffSamplePoint` 用的是同一公式，未做任何 16:9 特化。

本次仅在 16:9（1817×1025）实机验证；按上述机制其它宽高比应同样成立，但**未实测**。

## 已知限制与界面提示

**全屏独占模式不支持**：该模式下游戏不参与桌面合成，GDI 取色必然失败，Buff 守卫随之失效。
这不是可兼容的差异，而是与「不读内存、不注入、不加载驱动」技术路线绑定的硬约束。

处理方式：主窗口明确提示「⚠ 屏幕识别（保持Buff）需游戏窗口化运行」，ToolTip 里给出对策
（改用窗口化 / 无边框窗口化），避免用户面对失效的守卫去游戏里排查原因。

## 剩余未验证项

2. **其它宽高比的实际表现** —— 机制上自适应（见上），但只在 16:9 实测过。
